Expand description

A check that runs inside every write transaction of a PostgresEventStore, installed with PostgresEventStore::with_write_guard.

A guard lets an application make each event-store write conditional on database state that Arc does not own, atomically with the write itself. A typical use is a fencing check: the guard reads an application-owned epoch row FOR SHARE and refuses the write when this process is no longer the current writer, while the row lock keeps the epoch from advancing until the write has committed.

§When it runs

The guard runs exactly once per write transaction:

  • once per append, append_to or append_to_with_publication call, regardless of how many events the batch holds;
  • once per acknowledge_publication call;
  • once per save_snapshot call.

It is not called for an empty append batch, for a batch rejected by audit-metadata validation (both return before any transaction is opened), for any read (load*, stream_all, get_*version, pending_publications, load_snapshot*), or for initialize_schema.

§Transaction semantics

check receives the connection of the write transaction and is the first statement after BEGIN, before Arc reads the stream version. Therefore:

  • locks the guard takes are held until Arc commits or rolls back the write;
  • anything the guard writes commits or rolls back together with the write;
  • a guard failure takes precedence over [EventStoreError::ConcurrencyConflict] and [EventStoreError::InvalidSequence], which are detected later.

When check returns Err, Arc rolls the transaction back, persists nothing, and returns the guard’s error to the caller unchanged.

With a guard installed, acknowledge_publication and save_snapshot run in an explicit transaction (guard, statement, commit) instead of a single auto-commit statement. Without a guard they are unchanged.

§Rules for implementations

  • Do not commit or roll back the transaction, and do not issue SET TRANSACTION.
  • Do not leave session state changed (for example SET without LOCAL, session advisory locks, or temporary objects): the connection returns to the pool afterwards.
  • Avoid returning [EventStoreError::ConcurrencyConflict]; callers may treat it as a retryable optimistic-concurrency failure.
  • The guard runs under the pooled connection’s own timeouts (statement_timeout, lock_timeout, …); Arc adds none. A guard that blocks holds a pooled connection and delays the write.

§Scope

This is a PostgreSQL-only extension. The arc-core EventStore trait and arc-es-sqlite are unchanged, and PostgresReadModelStore is not guarded.
