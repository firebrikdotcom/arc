# Changelog

## Unreleased

## 0.9.4 — 2026-11-21

### Fixed

- `arc-es-sqlite`: the first read on a new store, or on a replacement connection, no longer
  stalls for seconds under nonstop commits in rollback-journal mode. The first statement on a
  connection loads the schema and needs a shared lock on the file; it ran outside the queue
  (r2d2's `SELECT 1` check at check-out, and the stores' question about the journal mode), so
  it polled with SQLite's unfair busy retry. Pools built by the stores (`new`) now lend
  connections without r2d2's check-out test, and the journal mode is asked as a queued read,
  so that first read waits for one commit like any queued read. SQLite connections do not go
  stale, and Diesel still has r2d2 discard a connection left in a broken transaction.
  Measured with four tasks appending nonstop for 12 seconds (rollback journal, real disk,
  3 runs): the first `get` on a fresh `SqliteReadModelStore::new` took at most 8.4, 6.0 and
  4.0 s before, with 8 of 15 attempts over 500 ms, and at most 7.8, 21.9 and 36.7 ms after,
  with none over 500 ms.
- Limit: a pool passed to `with_pool` keeps the caller's policy. With r2d2's default
  `test_on_check_out(true)`, each new connection's `SELECT 1` still runs outside the queue and
  can stall up to the connection's busy timeout. Build such a pool with
  `test_on_check_out(false)` when the file is shared with heavy writers. Connections opened
  outside the stores are unchanged. No public API, journal mode, durability or busy-timeout
  setting changes.

## 0.9.3 — 2026-11-21

### Security

- `arc-es-postgres` depends on `sqlx-core` and `sqlx-postgres` 0.8 directly instead of the
  `sqlx` facade crate. The facade kept its optional MySQL and SQLite drivers in `Cargo.lock`,
  which pinned `libsqlite3-sys` to 0.30 (RUSTSEC-2026-0459) and carried `rsa`
  (RUSTSEC-2023-0071). Arc's lockfile now resolves `libsqlite3-sys` 0.40 through Diesel, and
  both `cargo audit` exceptions are removed. The public API is unchanged: `sqlx::PgPool`,
  `sqlx::PgConnection` and `sqlx::Transaction` in the facade are re-exports of the same
  types, so applications on `sqlx` 0.8 compile without changes.
- `arc-web` and the reference application declared the `sqlx` SQLite driver only for its
  effect of compiling SQLite from bundled source. They now request that directly
  (`libsqlite3-sys` with `bundled`), so SQLite is still built in rather than linked from the
  system. Arc's own SQLite tests use Diesel.
- `arc new --android` no longer generates code on the `sqlx` SQLite driver. The generated
  `rust/src/schema.rs` and resource tests use Diesel, and `rust/Cargo.toml` requests
  `diesel` (`sqlite`), `libsqlite3-sys` with `bundled` (Android has no system SQLite) and
  `tokio` (`rt`, `sync`) instead of `sqlx`, so a new project's lockfile resolves `libsqlite3-sys`
  0.40 and no `sqlx` crate. The schema, the `arc_schema_migrations` ledger, the statements
  and the signature of `schema::initialize(path)` are the same. Its implementation differs:
  Diesel blocks, so the work runs on Tokio's blocking pool, or on a plain thread when the
  future is polled outside a Tokio runtime, and a panic in it is resumed in the caller.
  Once started, the work runs to commit or rollback even if the future is dropped. The
  connection closes on drop, so a close error is no longer reported, and a path passed
  directly to `schema::initialize` is opened as Diesel opens it (a `sqlite://` prefix is
  stripped and `file:` URIs are honoured); paths that go through `CoreKey::sqlite_file`
  never have those forms.
- An Android project generated by an earlier release keeps the `sqlx` driver and
  `libsqlite3-sys` 0.30 in its own lockfile. `rust/src/schema.rs` is a managed skeleton file
  with a recorded block, so move it by hand: replace the `sqlx` line in `rust/Cargo.toml`
  with the three dependencies above, copy `rust/src/schema.rs` from a freshly generated
  project while keeping the entries of its `MIGRATIONS` list, change the `PRAGMA
  journal_mode` check in each `rust/tests/<resource>.rs` likewise, and refresh
  `rust/Cargo.lock`.
- An application's own `Cargo.lock` decides its `libsqlite3-sys`. One that also depends on the
  `sqlx` facade keeps `libsqlite3-sys` 0.30 until it drops the facade or moves to a release
  of it that accepts the patched line.

### Fixed

- `arc-es-sqlite`: sustained contention inside one process no longer ends in
  `database is locked`. SQLite makes a connection that finds the file locked poll for it, and
  the first to poll after a commit wins, so under continuous writes one caller could lose
  every retry for the whole 5-second busy timeout although nobody held the file for long.
  `SqliteEventStore`, `SqliteReadModelStore`, `SqliteSessionStore` and `SqliteAccessLogger`
  now queue among themselves, per database file, before they enter SQLite: writers take turns
  first-in, first-out. In rollback-journal mode reads run together and beside a writer until
  it commits; a commit gives the reads already running 20 ms to finish, and reads that arrive
  during it all run before the next commit. In WAL mode reads are not queued. The queue is
  shared by all stores and pools of the process that open the same file, under any spelling
  of its path, and is held on the blocking thread for one operation, never across an `await`.
  No public API, journal mode, durability or busy-timeout setting changes.
- Read-model upserts, deletes and truncates, publication acknowledgements, snapshot saves and
  session writes now run as one `BEGIN IMMEDIATE` transaction each, as appends already did,
  instead of a bare statement. The effect of each is the same.
- Unchanged, and still bounded by the busy timeout: contention with another process or with
  a connection opened outside these stores (including `arc-auth-db` and an application's own
  Diesel pool on the same file), and a read that outlasts the 20 ms. A writer always makes
  its own attempt; time it queued behind attempts refused by such a lock is taken off that
  attempt's busy timeout. A queued writer has no deadline of its own, only the bounded
  writers ahead of it. In-memory databases are not queued.
- Two effects on connections that share the file but are not these stores (`arc-auth-db`,
  an application's own pool, `arc-web`'s `get_connection`), compared with 0.9.2:
  - Under a write-heavy load on a fast file system they get fewer turns. Store writers hand
    the write slot to each other directly, so the file is seldom free when an outside
    connection polls for it. Measured on tmpfs, four store writers against one outside
    writer for 8 seconds: 56 outside writes instead of 231 with a 5-second busy timeout; with
    500 ms, 62 writes and 10 `database is locked` instead of 335 and 1.
  - When an outside lock is held longer than the busy timeout, each store writer is held to
    its own timeout, so more callers can see `database is locked` than before: 10 of 10
    instead of 2 of 10 were measured in review for a 700 ms lock with a 300 ms timeout.

## 0.9.2 — 2026-11-19

All fourteen reusable crates are published to crates.io.

### Added

- `arc-es-postgres`: optional in-transaction write guard. `PostgresEventStore::with_write_guard`
  installs a `WriteGuard` whose `check` runs as the first statement of every write
  transaction (appends, publication acknowledgements, snapshot saves) on the same
  connection, so its locks are held until Arc commits and a refusal persists nothing.
  Additive: without a guard behaviour is unchanged. With a guard, publication
  acknowledgements and snapshot saves run in an explicit transaction instead of a single
  auto-commit statement. PostgreSQL only; `arc-core` and `arc-es-sqlite` are unchanged.

### Security

- Upgrade `actix-web` to 4.20, `actix-http` to 3.22 and `actix-files` to 0.7 (workspace
  requirement `0.7.4`), clearing the RustSec advisories against the earlier releases.
  Applications that also depend on `actix-files` directly should move to 0.7.
- `libsqlite3-sys` RUSTSEC-2026-0459 remains open: the patched line needs sqlx 0.9 in every
  crate, which changes the public pool and connection types of the storage adapters. It is an
  explicit `cargo audit` exception until that migration.

## 0.9.1 — 2026-11-06

All fourteen reusable crates are published to crates.io.

### Security and reliability

- Contain public asset paths, bind password confirmation to the signed-in account,
  and ignore untrusted forwarding headers in request/login throttles.
- Keep profile/password CSRF tokens valid across retries and repeated saves;
  prevent Turbo from prefetching the reference app's Sign out action.
- Queue NATS publication atomically with event persistence and retry automatically
  after failures/restarts, preserving event IDs and at-least-once delivery.
- Reconcile authoritative projection state under reordered/concurrent delivery;
  retain hidden versioned deletion tombstones to prevent stale replay restoring users.
- Include the publication queue in generated web/Android migrations and update
  generated projectors to reconcile authoritative state.
- Fail the CI summary on every unsuccessful dependency, including coverage, and
  identify/lock/clean up the exact browser-test server process.

### Operations

Existing SQLite deployments must apply the new `event_publications` migration before
using durable NATS publication. Custom stores opt in through the additive durable
publication APIs; the default command-bus mode remains unchanged. Committed NATS
writes succeed when durably queued even if the immediate broker call fails. Proxy
users share the socket peer's rate-limit bucket; enforce per-client limits at the edge.
Deployment audit policy remains pending owner approval.

All fourteen reusable packages move together at 0.9.1; publication status is tracked
in [Published Packages](docs/packages.md).

## 0.9.0 — 2026-10-31

Published to crates.io. `arc-stack` and `arc-ffi` are published for the first time.

### Breaking changes (Phase 2 security hardening)

Details and migration steps: [Upgrading](docs/upgrading.md#phase-2-security-hardening-090--compatibility-notes).

- The `/ws` handshake fails closed unless the app configures an origin
  allowlist and a principal provider ([Upgrading](docs/upgrading.md#phase-2-security-hardening-090--compatibility-notes)).
- Room subscriptions outside `user:<id>` are silently dropped
  ([Upgrading](docs/upgrading.md#phase-2-security-hardening-090--compatibility-notes)).
- Postgres `events.payload` is rewritten from JSONB to JSON at startup
  ([Upgrading](docs/upgrading.md#phase-2-security-hardening-090--compatibility-notes)).
- Event timestamps are stored at whole-second precision
  ([Upgrading](docs/upgrading.md#phase-2-security-hardening-090--compatibility-notes)).

### Fixed

- `arc new` no longer lets inherited `GIT_DIR` and related variables (for example under a Git hook) redirect `git init` to the caller's repository.

### Security

- Update `actix-http` to 3.20.0 (zstd 0.14.3, zstd-safe 8.2.0) to fix RUSTSEC-2026-0391 and RUSTSEC-2026-0403 in the locked workspace and `cargo install --locked` CLI; downstream apps resolve their own lock.
- Repair the Cargo.lock and package-lock.json dependency audit findings.

### Added and changed

- Phase 2 security hardening: WebSocket origin and identity authorization, and
  projection event-origin controls (see `docs/phase-2-security-hardening.md`).

- Add `arc new --android`, `arc doctor --android`, and
  `arc generate resource --ffi` for native Android app scaffolding. Generated
  projects depend on the published `arc-core`, `arc-stack`, and `arc-ffi`
  crates pinned to the CLI's own version; `--arc-path PATH` or `ARC_PATH`
  opts into a local Arc checkout for framework development.

- Add headless `arc-stack` for shared event-sourced stack assembly and retain
  the existing `arc-web` stack/config public paths as re-exports.
- Add `arc-ffi` native adapter infrastructure with an owned async runtime,
  shared core registry, and UniFFI support; Android uses FFI only while web UIs
  are for web deployments.
- Add `ArcAppBuilder::register_aggregate_with_stack` and `SharedStack` so an
  application can share a caller-built event-sourced stack with its HTTP
  handlers. Limits: in-process event bus only (`EVENT_BUS=nats` fails at serve
  with an error naming the aggregate); the caller owns projection rebuild at
  startup; the stack and `DATABASE_URL`/`DATABASE_DRIVER` must name the same
  database.
- SQLite event-store and read-model connections now use a 5-second busy timeout.
  Appends acquire an IMMEDIATE write transaction before reading the current
  version, so competing writers queue instead of failing immediately. A lock
  held longer than 5 seconds can still fail. Journal mode remains unchanged;
  see [Upgrading](docs/upgrading.md).
