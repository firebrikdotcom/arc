# Application Anatomy

This page explains the code generated by:

```bash
arc new my-app --ui
```

The generated application is intentionally small:

```text
src/
├── main.rs     application startup, setup, migration, and Arc runtime wiring
├── domain.rs   placeholder aggregate required by the current Arc runtime
├── routes.rs   incoming HTTP routes and route registration
└── ui.rs       Tera controller for the optional browser page
```

`ui.rs` exists only when you pass `--ui`.

## How the files connect

```text
main.rs
  ├── selects setup, migrate, or serve
  ├── starts ArcApp<AppAggregate>
  └── registers routes::config
          ├── routes.rs handles /health
          └── ui.rs handles / and renders resources/views/home.html
```

The generated `AppAggregate` does not yet participate in either route. It is a placeholder type that satisfies `ArcApp`'s aggregate generic until you replace it with a real domain aggregate.

## `src/main.rs`

`main.rs` is the composition root: the one place where configuration, database setup, the domain type, projectors, and HTTP routes are assembled.

### Module declarations

```rust
use crate::domain::AppAggregate;

mod domain;
mod routes;
mod ui;
```

- `mod domain` compiles `src/domain.rs`.
- `mod routes` compiles `src/routes.rs`.
- `mod ui` compiles `src/ui.rs`; it appears only in a `--ui` project.
- `AppAggregate` becomes the aggregate handled by Arc's injected `CommandBus`.

### Embedded application migrations

```rust
const MIGRATIONS: EmbeddedMigrations =
    embed_migrations!("./migrations");
```

The migrations belong to your application. They are compiled into your binary from your own `migrations/` directory. Arc packages do not silently search for or own your application schema.

### Command selection

```rust
let command = env::args()
    .nth(1)
    .unwrap_or_else(|| "serve".to_string());
```

This gives the generated binary three modes:

| Shell command | Binary mode | Purpose |
|---|---|---|
| `make setup` | `cargo run -- setup` | Create `.env`, secret, database, and migrations |
| `make migrate` | `cargo run -- migrate` | Run pending migrations |
| `make dev` | `cargo run` | Default `serve` mode |

### Setup lifecycle

```rust
if !Path::new(".env").exists() {
    let example = fs::read_to_string(".env.example")?;
    // Generate 64 random bytes and encode them as hexadecimal.
    fs::write(".env", example.replace("generate-me", &secret))?;
}
```

Setup creates `.env` only when it is missing. Running it again preserves the existing file and secret.

After loading `.env`, setup opens `DATABASE_URL` and executes the embedded migrations:

```rust
let mut connection = SqliteConnection::establish(&database_url)?;
connection.run_pending_migrations(MIGRATIONS)?;
```

### Server composition

```rust
ArcApp::builder()
    .register_aggregate::<AppAggregate>()
    .register_routes(routes::config)
    .serve(host.clone(), port)
    .await
```

This line is the boundary between your application and the framework:

1. `register_aggregate::<AppAggregate>()` tells Arc to create a typed command bus for that aggregate.
2. `routes::config` tells Arc which application routes to mount.
3. `serve` creates the Actix server and inserts framework data into it.

Handlers can then request:

```rust
web::Data<CommandBus<AppAggregate>>
web::Data<dyn ReadModelStore>
```

### Actix shared application data

> **Note:** [`web::Data`](https://docs.rs/actix-web/latest/actix_web/web/struct.Data.html) is how Actix gives a route access to shared application services. Arc creates services such as `CommandBus<ProductAggregate>` and `ReadModelStore` when the server starts; `web::Data<T>` asks Actix for the shared service of type `T`. This connects the HTTP layer to the application layer safely without creating a new service for every request.

The starter routes do not request either yet.

When you build a real domain, replace `AppAggregate` and register its projector:

```rust
ArcApp::builder()
    .register_aggregate::<ProductAggregate>()
    .register_projector(ProductProjector, "products_view")
    .register_routes(routes::config)
    .serve(host, port)
    .await
```

### Why the aggregate is in the builder

Each aggregate registration creates its matching command bus:

```rust
ArcApp::builder()
    .register_aggregate::<ProductAggregate>()
// creates and injects CommandBus<ProductAggregate>
```

Product controllers can then receive that bus:

```rust
async fn create_product(
    bus: web::Data<CommandBus<ProductAggregate>>,
) {
    bus.dispatch(product_command, context).await;
}
```

Here, [`web::Data`](#actix-shared-application-data) asks Actix's application container for the shared `CommandBus<ProductAggregate>`.

### What about multiple aggregates?

Register each writable aggregate explicitly:

```rust
ArcApp::builder()
    .register_aggregate::<ProductAggregate>()
    .register_projector(ProductProjector, "products_view")
    .register_aggregate::<OrderAggregate>()
    .register_projector(OrderProjector, "orders_view")
```

Arc creates both buses:

```rust
web::Data<CommandBus<ProductAggregate>>
web::Data<CommandBus<OrderAggregate>>
```

Actix distinguishes these [`web::Data`](#actix-shared-application-data) services by their complete Rust types, so a Product handler cannot accidentally receive the Order command bus.

Projectors and snapshot policies belong to the most recently registered aggregate. Register Product, configure Product, then register and configure Order.

## `src/domain.rs`

The generated domain file contains four concepts:

```rust
#[derive(Default)]
pub struct AppAggregate {
    version: i64,
}
```

### `AppAggregate`

An aggregate is a consistency boundary. A real aggregate stores enough state to enforce business rules when a command arrives.

The generated aggregate stores only `version`, so it has no business state and enforces no rules. It gives a new project one valid aggregate registration until you replace or supplement it with real domain aggregates.

```rust
pub struct AppCommand {
    aggregate_id: String,
}
```

### `AppCommand`

A command represents an intention to change one aggregate instance. `aggregate_id` tells `CommandBus` which event stream to load.

The generated command is not used by any route. Its field is private and it has no meaningful operation. It exists only to satisfy the `Aggregate::Command` associated type.

```rust
impl Command for AppCommand {
    fn aggregate_id(&self) -> &str {
        &self.aggregate_id
    }
}
```

`CommandBus` calls `aggregate_id()` before handling a command. It uses that ID to:

1. Load the aggregate's stored events.
2. Rebuild the aggregate by calling `apply` for each event.
3. Check the current stream version.
4. Append newly produced events with optimistic concurrency.

```rust
#[derive(Debug, Error)]
#[error("application command failed")]
pub struct AppError;
```

### `AppError`

`AppError` is the error type required by this line in the aggregate implementation:

```rust
type Error = AppError;
```

Every aggregate handler returns `Result<Vec<Event>, Self::Error>`. The generated handler has no behavior yet, so `AppError` is only a placeholder that lets the empty aggregate compile.

Replace it with errors that describe why a real command can be rejected:

```rust
#[derive(Debug, Error)]
pub enum ProductError {
    #[error("product already exists")]
    AlreadyExists,

    #[error("product name cannot be empty")]
    EmptyName,
}
```

The aggregate returns one of these errors when a command violates a business rule. The command bus passes that failure back to the controller, which decides which HTTP response to send. Rejected commands produce no events and make no state change.

```rust
async fn handle(
    &self,
    _command: Self::Command,
) -> Result<Vec<Event>, Self::Error> {
    Ok(Vec::new())
}
```

### `handle`

`handle` is where a real aggregate validates a command and produces events.

The generated implementation returns no events. Therefore, dispatching `AppCommand` would make no state change and persist nothing.

A real implementation looks like:

```rust
use arc_core::event::{Event, NewEvent};

async fn handle(
    &self,
    command: ProductCommand,
) -> Result<Vec<Event>, ProductError> {
    match command {
        ProductCommand::Create { id, name } => {
            if self.exists {
                return Err(ProductError::AlreadyExists);
            }

            Ok(vec![Event::new(NewEvent {
                aggregate_type: "Product",
                aggregate_id: id.clone(),
                sequence: self.version + 1,
                event_type: "ProductCreated",
                payload: serde_json::json!({ "id": id, "name": name }),
            })])
        }
    }
}
```

`NewEvent` is a parameter struct: its field names make every value's purpose explicit. Rust uses structs like this when a constructor would otherwise have several unclear positional arguments.

```rust
fn apply(&mut self, event: &Event) {
    self.version = event.sequence;
}
```

### `apply`

`apply` reconstructs aggregate state from facts that are already stored.

The placeholder remembers only the latest sequence number. A real aggregate also restores fields needed by its rules:

```rust
fn apply(&mut self, event: &Event) {
    if event.event_type == "ProductCreated" {
        self.exists = true;
        self.name = event.payload["name"]
            .as_str()
            .map(str::to_owned);
        self.version = event.sequence;
    }
}
```

`handle` decides whether something may happen. `apply` records what an already accepted event means for in-memory domain state.

## `src/routes.rs`

`routes.rs` is the HTTP entry layer.

```rust
#[get("/health")]
async fn health() -> impl Responder {
    HttpResponse::Ok().json(serde_json::json!({
        "status": "healthy",
        "application": env!("CARGO_PKG_NAME"),
        "version": env!("CARGO_PKG_VERSION")
    }))
}
```

This is an Actix controller:

1. `#[get("/health")]` declares the method and path.
2. No request data is needed.
3. The handler constructs a JSON response.
4. No aggregate, command, event, or database is involved.

Routes become active only when registered:

```rust
pub fn config(cfg: &mut web::ServiceConfig) {
    cfg.service(health)
        .service(crate::ui::home)
        .service(actix_files::Files::new("/public", "public"));
}
```

- `health` mounts the JSON health controller.
- `ui::home` mounts the optional Tera controller.
- `Files` maps `/public/*` URLs to files in `public/`.

For larger applications, keep `config` here and move controllers into modules such as `src/http/products.rs`.

## `src/ui.rs`

`ui.rs` is the controller layer for the optional generated page:

```rust
#[get("/")]
pub async fn home() -> impl Responder {
    let template =
        include_str!("../resources/views/home.html");
    let mut context = Context::new();
    context.insert("app_name", env!("CARGO_PKG_NAME"));

    match Tera::one_off(template, &context, true) {
        Ok(html) => HttpResponse::Ok()
            .content_type("text/html; charset=utf-8")
            .body(html),
        Err(error) => HttpResponse::InternalServerError()
            .body(format!("template error: {error}")),
    }
}
```

Its responsibilities are:

1. Receive `GET /`.
2. Build view data in a Tera `Context`.
3. Render `resources/views/home.html`.
4. Return HTML or an error response.

There is no database model in this controller. For a projected Product view, the handler would request [`web::Data<dyn ReadModelStore>`](#actix-shared-application-data), query `products_view`, insert the result into the Tera context, and render it.

## Outside `src/`

| Path | Role |
|---|---|
| `resources/views/home.html` | Tera view rendered by `ui::home` |
| `public/styles.css` | Static stylesheet served at `/public/styles.css` |
| `migrations/` | Event-store schema plus tables for your projections |
| `.env.example` | Committed configuration template |
| `.env` | Local generated configuration and secret; never commit |
| `Makefile` | Short commands for setup, run, migrate, check, and test |
