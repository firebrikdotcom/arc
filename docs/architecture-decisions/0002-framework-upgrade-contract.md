# ADR 0002 — Framework upgrade contract: ownership boundary, SemVer policy, and upgrade path

- Status: **Accepted**
- Date: 2026-07-01
- Deciders: Arc framework architecture
- Related: [ADR 0001](0001-benthos-only-event-routing.md), [Event Handlers](../event-handlers.md),
  [Publishing Crates](../publishing-crates.md), and `progress.md` ("Framework readiness")

## Context

Arc started as a clone-and-edit starter: framework code (`crates/arc-*`, `config/benthos/`,
migrations) and application code live in one tree, edited by the same hands. That shape is fatal
for upgradeability — once a user has hand-edited framework files, there is no clean way to deliver
them a newer `arc-core` or a fixed Benthos generator. They are forked from minute one.

ADR 0001 already drew the right line on the routing plane: users extend event handling by writing
**handler manifests** (`config/handlers/*.yaml`); the runtime pipeline is **generated** into
`config/benthos/generated/` and is never hand-edited. This ADR generalizes that
authored-vs-generated split into a whole-framework ownership contract, and attaches the versioning
policy and upgrade path that make "upgrade without starting from scratch" a stated guarantee
instead of a hope.

The reusable crates (`arc-core`, `arc-es-sqlite`, `arc-es-postgres`, `arc-es-nats`, `arc-web`) share
the workspace version (currently `0.8.6`). The reusable crates have publish-ready metadata;
the v0.8.6 release workflow completed successfully. `arc-web` is the framework web/runtime crate; `arc-app`
(package `arc`) is the thin user-owned application template that depends on it.

## Decision

### 1. The upgrade promise

> A user on Arc `x.y` can move to `x.(y+1)` by bumping the `arc-*` dependency versions,
> re-running the generators (`make benthos-config`), and running the shipped migrations —
> without re-applying hand edits to Arc-owned files.

Everything below exists to make that promise checkable. A file is in exactly one ownership class;
"shared" files are a contract violation to be fixed, not a category.

### 2. Ownership boundary

**Machine-owned (generated).** Regenerated from inputs; never hand-edited. Every generated file
carries a `# Generated by … do not edit` banner naming its inputs and regeneration command. CI
verifies freshness (`make benthos-config-check` today; the `make doctor` drift guard extends
this).

| Path | Generated by | Regenerate with |
|---|---|---|
| `config/benthos/generated/**` | `scripts/generate-benthos-config.mjs` from `config/handlers/*.yaml` | `make benthos-config` |
| `crates/arc-app/src/schema.rs` | Diesel `print_schema` from `migrations/` | `diesel migration run` / `diesel print-schema` (configured by `diesel.toml`) |
| `dist/**` | Vite from `crates/arc-app/src/resources/{css,js,imgs}` | `make frontend-build` |

**Arc-owned (framework).** Shipped and upgraded by Arc; users must not edit these in place.
Changes arrive by bumping the crate/repo version. Local edits to Arc-owned files fork the
installation and void the upgrade promise.

- `crates/arc-core`, `crates/arc-es-sqlite`, `crates/arc-es-postgres`, `crates/arc-es-nats`
  (published crates — the supported way to consume them is by version, not by editing sources).
- `crates/arc-web` — reusable framework web/runtime crate (Actix bootstrap, middleware, session
  and JWT helpers, CLI commands, base server wiring, websocket transport, and the generic
  event-sourced stack `EsStack<A>`). Generic over the application's aggregate: it ships
  auth/session *machinery* but no concrete domain type and no application controllers. Consumed
  by apps via `ArcApp::builder()`; not hand-edited in a user installation.
- `scripts/generate-benthos-config.mjs` and its tests (the manifest compiler).
- `config/benthos/events.yaml` (Arc's reference/base pipeline; the runtime artifact is the
  generated file).
- Framework-shipped Diesel migrations in `migrations/` (events table, snapshots, audit columns,
  JWT sessions, integrity signatures, `users_view`).

**User-owned.** Arc never overwrites these. Upgrades touch them only via documented, reversible
migrations (and always announced in release notes).

- `config/handlers/*.yaml` — handler manifests (the extension surface per ADR 0001).
- `.env` and deployment configuration.
- The thin application crate `crates/arc-app` (package `arc`): domain aggregates, app services,
  validation, app-owned controllers/routes mounted via `register_routes`, templates/assets under
  `src/resources/**`, and app seeders.
- Domain code: `crates/arc-app/src/domain/**` (aggregates, commands, projectors — scaffolded
  once by `make new-aggregate` / `scripts/new-aggregate.sh`, then owned by the user).
- `crates/arc-app/src/services/`, `src/validation/`, `src/http/controllers/` — all app-owned,
  including the auth/admin/API/diag controllers. They bind the concrete `UserAggregate`, so they
  live with the domain in the app, not in the framework.
- Templates and assets: `crates/arc-app/src/resources/**` (Tera views, CSS, JS, images).
- Application migrations and seeders (`crates/arc-app/src/database/seeders/`, user-added
  directories under `migrations/`).

**Known boundary debt.** The physical split has landed: framework runtime lives in `crates/arc-web`;
`crates/arc-app` is the thin user template that depends on it via `ArcApp::builder()`. Remaining
upgradeability work is packaging and distribution, not the ownership classification:

- Publish `arc-web` (and keep it versioned in lockstep with the other `arc-*` crates).
- Ship an `arc new` CLI (or equivalent) so apps start from a thin template instead of
  clone-and-edit of this monorepo.

There is exactly one copy of the `User` domain — in `crates/arc-app`. `arc-web` ships no concrete
domain type. Applications use `ArcApp::builder().register_aggregate::<A>()` once per writable
aggregate, producing a distinct typed `CommandBus<A>` for each registration.

`make doctor` enforces the machine-owned generated boundary and the structural Arc-owned
boundary (Arc-owned runtime trees must not reappear under `crates/arc-app/src`).

### 3. SemVer and public API policy

**Versioning strategy.** All `arc-*` crates version in **lockstep** with the workspace version
through `0.x` (simplest to reason about pre-1.0; adapter crates pin `arc-core` by exact version).
Independent versioning is deferred until `1.0`.

**Pre-1.0 SemVer rules.**

- Within a `0.y.z` line, `z` bumps are backward-compatible: additive APIs, bug fixes, doc changes.
- Breaking changes bump the minor version (`0.y` → `0.(y+1)`) and are listed in release notes
  with a migration note per break.
- After `1.0`, standard SemVer applies: breaking changes only at major versions.

**Public API surface.** The following are covered by the compatibility rules above:

1. **`arc-core` traits and core types**: `Event`, `EventStore` (incl. `VersionCheck`,
   `Snapshot`, `save_snapshot`/`load_snapshot`), `EventBus`/`EventHandler`, `Aggregate`
   (incl. `to_snapshot`/`from_snapshot`), `Projection`/`Projector`/`ProjectionEngine`,
   `CommandBus`/`SnapshotPolicy`, `ReadModelStore`, `AuditMetadata`/`audit_context`,
   `AccessLogger`/`Sensitivity`/`FailurePolicy`, `SessionStore`, `IntegrityChain`.
2. **The event envelope** delivered by Benthos to handlers ([Event Handlers](../event-handlers.md) §1).
   It self-versions via `envelope_version`: new **optional** fields are additive and do **not**
   bump it; breaking envelope changes bump `envelope_version` **and** the crate minor version.
   Handlers must tolerate unknown fields.
3. **The handler manifest schema** (`config/handlers/*.yaml`) and its compiled semantics:
   delivery targets (HTTP/NATS only — SQL/database delivery is rejected and stays rejected),
   retry meaning (`max_attempts` = total attempts), idempotency/dedupe keys, and DLQ behavior
   (`dlq.*` subjects, `x_arc_dlq` metadata). New manifest keys are additive; removing or
   re-meaning a key is a breaking change.
4. **NATS subject naming**: `events.<aggregate_type>.<event_type>` (snake_case) and the
   `EVENTS`/`ARC_DLQ` stream provisioning behavior.
5. **Storage schemas shipped by framework migrations**: changes arrive only as new Diesel
   migrations, never as edits to shipped migrations.

Anything not listed — crate internals, `arc-web` bootstrap wiring,
`arc-app` template views, the base `config/benthos/events.yaml` pipeline internals, scripts — is
not public API and may change in any release.

**Deprecation policy.** Deprecated traits, methods, and manifest keys carry `#[deprecated]` (or a
documented warning for YAML/config surfaces) for at least one minor release before removal.
Additive evolution is always preferred for event payloads and read-model/audit/session/integrity
structs: `event_type` payloads add fields, never repurpose them.

### 4. Supported upgrade path

The supported upgrade procedure for a user application, per release:

1. **Read the release notes** — every breaking change ships with a migration note.
2. **Bump the `arc-*` dependency versions** in the app's `Cargo.toml` (lockstep: one version).
3. **Run shipped migrations** — `make migrate`. Framework schema changes are always new
   migrations; Postgres self-initializes via `build_stores`.
4. **Regenerate machine-owned files** — `make benthos-config` (and `make frontend-build` where
   applicable). Generated files must never contain manual edits, so regeneration is always safe.
5. **Re-validate** — `make doctor`, `make test`, `make lint`, `make benthos-lint` (and `make e2e`
   when browser flows are in scope).

Per-surface compatibility rules:

- **Database schema**: forward-only Diesel migrations; shipped migrations are immutable.
- **Event envelope**: additive within an `envelope_version`; handlers tolerate unknown fields;
  old handlers must keep parsing new envelopes within the same `envelope_version`.
- **Handler manifests**: unknown keys are rejected at generation time, so a manifest that
  compiles today keeps compiling within the same minor line; manifest-schema breaks arrive with
  a generator that upgrades manifests or fails with a precise message.
- **Integrity chain**: enabling `EVENT_INTEGRITY_KEY` on existing data requires an event replay/
  reseal. This is a documented migration step, not a silent config flip.
- **Event data**: the event log is immutable; upgrades never rewrite stored events. Read models
  may be rebuilt from the log at any time (projection replay), which is the standard recovery
  path when a projection changes shape.

The user-facing walkthrough of this procedure is [Upgrading](../upgrading.md); this ADR is the
normative contract it implements.

## Consequences

### Positive

- The generated/authored line from ADR 0001 becomes a whole-framework rule, checkable by tooling:
  `make doctor` / `make arc-check` specify "drift" as a generated file that is stale against its
  inputs, a generated file with manual edits, or Arc-owned runtime trees reintroduced under the
  user template.
- "What is public API" is now written down, so publish decisions, review comments, and breaking-
  change calls have a reference instead of case-by-case judgment.
- The `arc-web` / thin `arc-app` split matches the ownership classification: framework runtime
  upgrades via crate version bumps; user code stays in the app template.

### Negative / costs

- Lockstep versioning forces version bumps on crates with no changes; accepted as the pre-1.0
  simplicity trade-off.
- Until `arc-web` is published and `arc new` ships, many apps still consume Arc as a monorepo
  clone; the ownership boundary is enforceable in-tree (`make doctor`) but the end-user install
  path is not yet package-only.
- Declaring the manifest schema public API means generator changes need the same review rigor as
  Rust trait changes.

### Neutral

- [Publishing Crates](../publishing-crates.md) keeps the operational publish procedure; its policy section
  now defers to this ADR.

## Follow-ups

- Publish `arc-web` under the same lockstep SemVer policy as the other `arc-*` crates.
- Ship `arc new` (or equivalent) so applications start as thin templates depending on versioned
  crates rather than clone-and-edit of this monorepo.
- Add banner + freshness checks for `crates/arc-app/src/schema.rs` and `dist/` (Benthos generated
  config and the Arc-owned structural boundary under `crates/arc-app/src` are checked today).
